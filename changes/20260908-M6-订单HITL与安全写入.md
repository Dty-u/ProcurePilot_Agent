# M6 订单 HITL 与安全写入 Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 实现缺字段补充、参数绑定审批、一次性执行、幂等写入和完整审计的订单操作链路。

**Architecture:** 写操作分为 prepare、supplement、approve/reject、execute 四个阶段。LangGraph interrupt 负责暂停流程，业务层的 `ApprovalGrant` 才是执行授权；最终写工具必须重新验证权限、参数哈希、过期时间、幂等键和版本。

**Tech Stack:** Python、Pydantic、hashlib、MySQL、LangGraph interrupt、pytest

---

## 前置条件与红线

- M3 事务和 M4 MCP 错误契约通过。
- Agent 和模型永远不能创建审批记录或自行批准。
- `order_create`、`order_update`、`order_cancel` 均不得自动重试。

### Task 1: 订单操作与规范化哈希

**Files:**
- Create: `src/procurepilot/business/order_operations.py`
- Test: `tests/unit/business/test_order_operation_hash.py`

定义 `OrderOperation`：operation_id、action、user_id、thread_id、normalized_payload、payload_hash、status、created_at、expires_at。action 仅允许 create、update、cancel。

参数哈希流程固定为：业务 Schema 校验 → ID、Decimal、币种和时间规范化 → JSON key 排序并使用稳定分隔符编码 → SHA-256。哈希输入至少绑定供应商、物料、数量、币种、报价引用、目标订单和 expected_version。

先写测试证明：字段顺序不影响哈希；`50` 与 `50.0` 规范化后相同；关键字段变化导致哈希变化；额外字段被拒绝；哈希内容不包含密钥和用户自然语言原文。

### Task 2: 缺字段补充

**Files:**
- Create: `src/procurepilot/agent/order/info_request.py`
- Test: `tests/contract/agent/test_order_info_interrupt.py`

订单字段不完整时，生成结构化 `order_info_request` interrupt，包含缺失字段、安全提示和已确认摘要。恢复格式为 `{"supplement": "..."}`，恢复内容重新经过 Schema 和业务预校验；模型不得猜测 supplier ID、part ID、数量、币种或 expected_version。

测试连续两次补充、无关补充、恶意提示注入、类型错误以及最终字段完整。

### Task 3: 审批实体与一次性授权

**Files:**
- Create: `src/procurepilot/business/approval.py`
- Modify: `src/procurepilot/business/services/order.py`
- Test: `tests/unit/business/services/test_order_approval.py`

定义 `ApprovalGrant`：approval_id、operation_id、approver_user_id、thread_id、action、payload_hash、decision、created_at、expires_at、consumed_at。审批由可信 API/应用服务创建，不向 Agent 暴露创建审批的普通工具。

执行前同时验证：审批为 approve、未过期、未消费、用户和 thread 匹配、action 匹配、payload_hash 匹配。任一失败均失败关闭。reject 将 operation 标为 rejected，零业务写入。

### Task 4: 三个安全写工具

**Files:**
- Create: `src/procurepilot/mcp_server/tools/order_writes.py`
- Test: `tests/contract/test_order_write_tools.py`

实现稳定工具名：`order_create`、`order_update`、`order_cancel`。工具参数只接受 operation_id、approval_id、idempotency_key，以及 update/cancel 所需 expected_version；真实规范化业务参数从已保存 operation 读取，禁止模型在执行时替换。

工具重新调用 `OrderService.execute()`，不得直接操作 Repository。失败返回稳定信封，不将审批失败伪装为普通业务提示。

### Task 5: MySQL 原子事务和攻击场景

**Files:**
- Test: `tests/integration/test_order_hitl_transaction.py`
- Test: `tests/security/test_order_approval_security.py`

覆盖：批准成功仅创建一次；拒绝零写入；审批后参数变化；跨用户、跨线程、过期、重复消费；并发审批执行；版本冲突；审计失败回滚；Prompt 声称“已经批准”仍不能执行。

审批消费、订单写入、幂等结果和审计必须处于同一事务。幂等重放返回原结果，但不得再次消费审批或新增审计中的“首次创建”事件。
