# M3 MySQL 持久化与迁移 Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 使用 MySQL 8.0 持久化采购业务数据，并保持 M2 的 Service 与 Repository 接口不变。

**Architecture:** SQLAlchemy ORM 只存在于基础设施层，领域层不感知数据库。所有写入由异步 Unit of Work 管理事务，Alembic 管理可升级和可回滚的 DDL。

**Tech Stack:** MySQL 8.0.44、SQLAlchemy 2.x async、aiomysql、Alembic、pytest

---

## 前置条件与安全边界

- M2 全部测试通过。
- 本机 `MySQL80` 服务可用；凭据由用户写入未跟踪的 `.env`。
- 开发库固定 `procurepilot_dev`，测试库固定 `procurepilot_test`。
- 自动测试遇到数据库名不含 `test` 或 `APP_ENV=production` 必须立即失败。

### Task 2: ORM 映射与首个迁移

**Files:**
- Create: `src/procurepilot/infrastructure/orm_models.py`
- Create: `alembic.ini` and `alembic/`
- Test: `src/tests/integration/test_migrations.py`

表至少包含 suppliers、parts、supplier_quotations、inventory_items、purchase_orders、purchase_order_items、order_operations、approval_grants、idempotency_records、operation_audits。

约束：

- `supplier_code`、`part_code`、`order_no`、`idempotency_key` 唯一。
- 金额使用 `DECIMAL(19,4)`，数量使用 `DECIMAL(19,6)`。
- 外键和状态字段不可为空。
- `version` 初始为 1。
- 时间统一按 UTC 写入；读取后由适配层恢复带时区对象。
- 审计记录只追加，不提供普通更新路径。

先执行 upgrade，再验证表和约束；执行 downgrade 到 base；再次 upgrade，证明迁移可重放。

### Task 4: 原子事务、幂等和乐观锁

**Files:**
- Test: `src/tests/integration/test_mysql_order_transaction.py`

先写失败测试：

- 订单已写入但审计失败时，订单回滚。
- 两个事务基于同一 version 更新，只有一个成功。
- 同一幂等键并发提交，只产生一张订单。
- 失败事务不会留下已消费审批。

更新语句必须包含 `WHERE id=:id AND version=:expected_version`，受影响行数不是 1 时转换为 `ConflictError`。唯一键冲突转换为稳定业务错误，原始 SQL 和 DSN 不上抛。
