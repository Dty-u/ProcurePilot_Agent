# 工程架构

## 核心原则

项目采用“Python 采购业务 + MCP 工具 + Deep Agent 编排 + FastAPI/SSE”的分层架构。Python 业务层是业务数据和规则的唯一权威来源，Agent 不直接操作数据库。

## 目标目录

`src/` 是项目源码根目录，采用“核心业务包 + Harness 运行包并列”的结构：

- `src/procurepilot/` 保留现有代码，继续存放全局配置、领域业务和基础设施实现。
- `src/agent/`、`src/api_view/`、`src/mcp_server/`、`src/skills/` 与 `procurepilot/` 并列，不再放入 `procurepilot/`。
- M0–M10 必须按照下列路径创建文件；`tests/` 只列测试分类目录，不展开具体测试文件。

根目录 `web/` 是独立于 Python wheel 的 Vue 3 工作台。它只调用 `api_view` 暴露的 HTTP/SSE 契约，不得直接访问 MySQL、MCP、Agent 状态或任何密钥；其本地开发身份只能通过未提交的 `.env.local` 转换为受控 Header。

### 目录命名约束

- `src/procurepilot/` 保留现有核心代码；不得把已经存在的 `business/`、`infrastructure/` 和 `config.py` 迁出该包。
- 新增的 `agent/`、`api_view/`、`mcp_server/`、`skills/` 和 `tests/` 是 `src/` 的直接子目录，禁止再创建到 `src/procurepilot/` 内。
- Python 包目录使用 `snake_case`；Skill 资源目录按约定保留 `supplier-comparison` 这类短横线名称，但不能作为 Python import 路径。
- 核心业务导入使用 `from procurepilot.business... `；Harness 层导入使用 `from agent... `、`from api_view... ` 或 `from mcp_server... `。
- 测试目录按 `unit`、`contract`、`integration`、`security`、`e2e` 分类，并尽量与生产模块职责对应；架构树不展开具体测试文件。
- `business` 定义接口，`infrastructure` 实现接口；不得为了复用 ORM 而让 `business` 反向导入 `infrastructure`。
- 根目录的 `alembic/` 只管理业务 MySQL DDL；Agent Checkpoint 表由独立 Checkpoint 数据库中的 `langgraph-checkpoint-mysql` 管理，用户 Store、展示消息和 Sandbox 文件不进入业务迁移。

## 分层职责

| 层 | 职责 | 禁止事项 |
| --- | --- | --- |
| `business` | 实体、业务规则、状态机、事务、幂等 | 依赖 Agent、FastAPI 或 MCP |
| `infrastructure` | ORM 映射、MySQL Repository、连接和事务适配 | 改变领域对象或编写业务规则 |
| `mcp_server` | 参数适配、权限上下文、错误映射 | 编写核心业务规则 |
| `agent` | 意图识别、委派、工具编排、结果整理 | 直接写数据库或自主审批 |
| `api_view` | HTTP 校验、SSE 转换、中断恢复 | 暴露 LangGraph 内部状态 |
| `skills`/Sandbox | 按需加载技能、隔离执行、临时产物 | 保存业务主数据 |

依赖方向：`api_view → agent → mcp_server → business services → repository protocols`；`infrastructure` 只实现 `business` 定义的接口，反向依赖不成立。

## MySQL 持久化边界（M3）

- SQLAlchemy ORM 仅存在于 `infrastructure`，领域实体不引用 ORM、Session 或数据库类型。
- `AsyncSession` 只在 `MySQLUnitOfWork` 生命周期内存活，Service 与调用方只获得领域对象。
- DDL 只由 Alembic 管理；自动测试必须使用 `APP_ENV=test` 且数据库名包含 `test`。
- 数据库完整性错误映射为稳定 `ConflictError`，其他 SQLAlchemy 错误映射为 `InfrastructureError`，不向业务层透出 SQL 或 DSN。

## Agent 边界

- 主 Agent：路由、委派、通用问答和最终回复。
- `procurement-analyst`：查询、比价、分析、图表和报告，只读业务数据。
- `procurement-order`：收集和校验订单信息，审批后调用写工具。

M7 的主 Agent 由异步 `create_main_agent` 工厂创建，向 `create_deep_agent` 显式传入 model、
tools、subagents、system prompt、checkpointer、store、backend、interrupt、middleware 和
context schema。子 Agent 分别传入独立工具列表，禁止依赖默认工具继承获得业务权限。当前
路由先识别分析与订单意图；混合读写请求先交给分析 Agent，随后必须由用户另行明确发起写操作。

分析、订单和主 Agent 的图均由 `create_deep_agent()` 编译，不直接调用 LangChain
`create_agent()`。DeepAgents 0.4.12 自动添加的 todo、task 和文件工具属于框架能力，
不计入采购业务授权。FastAPI 生产装配必须注入 `DeepAgentsSandboxBackend`，文件、Shell 和 Skill 脚本全部委托 OpenSandbox，禁止宿主回退。`StateBackend` 默认值只保留给不执行 Shell 的单元/契约测试和 CLI 兼容边界。

M8 已将 `AIOMySQLSaver` 和 `AIOMySQLStore` 接入主 Agent 装配，并新增 MySQL 展示消息
Repository。Checkpoint、Store、一次性 Resume 元数据和展示历史使用独立于业务库的 Agent
MySQL 数据库，并通过不同表保持职责隔离。thread 所有权、中断消费和用户偏好均由可信运行
上下文限定。M9 Skill 只从仓库审核白名单同步到请求级 Sandbox；M10 API 在每个 SSE 请求内绑定可信身份、MCP 和 Sandbox 生命周期。

## 存储边界

| 数据 | 存储/作用域 |
| --- | --- |
| 供应商、物料、报价、库存、订单 | Python 业务数据库/业务 ID |
| Agent checkpoint | Checkpointer/`thread_id` |
| 用户偏好 | StoreBackend/`user_id` |
| 展示消息 | 消息仓储/`thread_id` |
| 临时脚本、分析、报告 | OpenSandbox/sandbox ID + TTL |

## Service 与 Repository 边界（M2）

```text
调用方 → Service → UnitOfWork → Repository Protocol → 存储实现
```

- Service 只编排领域对象、权限、审批和事务，不使用 SQL 或存储细节。
- Repository 只提供强类型查询与保存，查询条件为显式对象，不接受任意 SQL、字典或字段名。
- Unit of Work 每次使用独立工作副本；只有显式 `commit()` 才对外可见，未提交、异常和审计失败都整体回滚。
- InMemory 实现是当前的可执行契约和测试替身，不是生产持久化方案；后续数据库实现必须遵循同一 Protocol 与事务语义。
- 业务错误使用领域错误层级，不在 `business` 层返回 HTTP 状态码或 MCP 错误信封。

## 写操作安全链路（M6）

`OrderService.prepare` 保留 M2 兼容链路；M6 的生产安全入口是 `execute_saved`。它只读取
`OrderOperation` 的不可替换参数快照，通过 `ApprovalGrant` 校验用户、thread、动作、哈希、
过期和一次性消费，再在同一 Unit of Work 内写入订单、操作状态、审批消费和审计。MCP 不
直接访问 Repository，可信审批写入也不向 Agent 暴露。

## 固定约束

- `DeepAgents==0.4.12`，升级必须单独验证兼容性。
- 模块导入不发起网络连接或创建 Agent；FastAPI `lifespan` 使用异步初始化。
- 写工具必须经过权限、业务校验、HITL、幂等和审计。
- 不需要时不引入 Redis、向量数据库或知识图谱。
