# 业务模型

## 核心角色

- 采购用户：查询、分析、提交订单信息和发起操作。
- 审批用户：批准或拒绝订单写操作。
- 主 Agent：识别意图并委派，无审批权。
- 分析子 Agent：生成证据化分析，不修改订单。
- 订单子 Agent：收集和校验参数，审批后调用写工具。

## M1–M7 已实现范围

当前已实现领域模型、Service/Repository 边界、MySQL 持久化、MCP 工具、采购分析 Agent、订单 HITL 安全写入、Multi-Agent 编排、MySQL Checkpoint/Store、OpenSandbox/Skills 和 FastAPI/SSE。业务规则仍以 Service 与 MySQL 事务为权威，API 和 Agent 不绕过该边界。

## M2 Service 能力

| Service | 已实现行为 |
| --- | --- |
| `SupplierService` / `PartService` | 通过显式查询对象搜索供应商和物料 |
| `QuotationService` | 查询指定时点仍有效的报价 |
| `InventoryService` | 返回可用量低于或等于安全库存的预警项 |
| `ComparisonService` | 按价格、交期排序，并保留每个报价被排除的明确原因 |
| `OrderService.prepare` | 预校验权限、供应商/物料状态、报价、币种、单位和 MOQ，不产生持久化写入 |
| `OrderService.execute` | 通过审批和报价复验后，幂等、原子地写入订单与审计 |

比价不做汇率换算：币种不一致时明确排除。同价时交期更短者优先。报价过期、MOQ 不满足、单位不一致和供应商停用都会作为可追溯排除原因返回。

## 已实现业务不变量

- `Money` 和 `PositiveQuantity` 只接受 `Decimal`，拒绝 `float`；数量必须大于零。
- `Money` 按币种精度量化，不同币种不能相加。
- 领域时间必须带时区，进入实体后归一化为 UTC。
- 实体 ID、业务 code 和必要名称不得为空；供应商、物料和有限状态不能用任意字符串绕过枚举。
- 禁用供应商或物料不能进入采购候选。
- 报价只在生效时间和截止时间之间有效，采购数量必须满足相同单位的 MOQ。
- 可用库存固定由“现有量减预留量”计算，调用者不能传入派生值。
- 订单行金额和订单总额由领域对象计算，调用者不能提交伪造金额。

订单状态迁移固定为：

```text
DRAFT → PENDING_APPROVAL → APPROVED → CREATED → CANCELLED
                         ↘ REJECTED
```

不在图中的直接迁移一律拒绝，`CANCELLED` 订单不能再修改订单项。

## 比价分析流程

```text
明确物料、数量、币种和时间范围
→ 查询内部数据和允许的外部报价
→ 统一单位并检查报价有效性
→ 比较价格、交期、质量和风险
→ 生成图表、报告、推荐及限制说明
```

外部网页报价只能作为带来源和时间的证据，不能自动覆盖内部权威数据。信息不足时必须明确说明，不得编造。

## 订单流程

```text
提取参数 → 查询实体 → 业务预校验
→ 缺字段时中断补充 → 展示操作摘要
→ 人工审批 → Python 业务层执行 → 返回真实结果
```

`OrderOperation` 保存经严格 Schema 校验后的规范化参数和 SHA-256；`ApprovalGrant` 同时绑定用户、thread、动作和参数哈希，并具有有效期和一次性消费状态。可信 API/UI 使用 `record_approval` 写入决定，Agent 没有创建审批的工具。`execute_saved` 只读取已保存参数；审批消费、订单、操作状态和审计在同一 UoW 中提交，幂等重放不重复消费审批或新增首次写入审计。
