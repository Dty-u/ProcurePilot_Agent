# 接口与事件模型

本文记录已实现的 MCP、HTTP 和 SSE 契约。

## MCP 工具

只读工具的身份来自服务端可信上下文，业务参数不接收 `user_id` 或 `roles`：

| 工具 | 输入字段 | 最大 `limit` | 主要返回信息 |
| --- | --- | ---: | --- |
| `supplier_query` | `keyword?`, `status?`, `limit=20` | 50 | 编码、名称、状态、评分、版本 |
| `part_query` | `keyword?`, `status?`, `unit?`, `limit=20` | 50 | 编码、规格、单位、状态 |
| `part_by_supplier` | `supplier_id`, `at`, `limit=20` | 50 | 在指定时刻有有效报价的物料 |
| `quotation_query` | `part_id?`, `supplier_id?`, `currency?`, `unit?`, `quantity?`, `at`, `limit=20` | 100 | 报价 ID、价格、币种、MOQ、单位、来源、采集时间、有效期 |
| `inventory_warning` | `part_id?`, `warehouse_code?`, `limit=20` | 100 | 在手、预留、可用、安全库存及版本 |
| `order_search_details` | `order_id?`, `order_no?`, `supplier_id?`, `status?`, `limit=20` | 50 | 订单行、总额和乐观锁 `version` |

`order_search_details` 仅允许 `order_reader` 或 `admin`；其余只读工具仅允许
`procurement_reader` 或 `admin`。所有查询受 `REQUEST_TIMEOUT_SECONDS` 限制。

写工具：`order_create`、`order_update`、`order_cancel`。创建工具只接收
`operation_id`、`approval_id`、`idempotency_key`；修改/取消另外接收
`expected_version`。未知业务字段会被 Pydantic 拒绝，工具不能覆盖已批准参数。写工具只调用
`OrderService.execute_saved()`，并重新验证权限、thread、哈希、有效期、审批、幂等键和版本；
三种写操作均不自动重试。

工具统一返回：

```json
{"ok": true, "data": {}, "error": null, "trace_id": "追踪标识"}
```

失败时 `ok=false`，`error` 提供稳定错误码和安全信息，不返回内部堆栈。

固定错误码为：`VALIDATION_ERROR`、`NOT_FOUND`、`CONFLICT`、
`PERMISSION_DENIED`、`APPROVAL_REQUIRED`、`DEPENDENCY_TIMEOUT`、`INTERNAL_ERROR`。
依赖超时可重试；未识别的内部错误只向客户端返回安全消息，并通过 `trace_id` 关联日志。

MCP 默认使用 `streamable-http`，监听 `127.0.0.1:8001`；FastAPI 默认端口为
`18000`，配置加载时会拒绝两个服务共用端口。未接入可信鉴权适配器时，默认调用方上下文
会失败关闭。

## HTTP

- `POST /api/chat/stream`：发送消息并返回 SSE；`user_id` 来自鉴权上下文。
- `POST /api/chat/{thread_id}/resume`：恢复补充或审批中断。
- `GET /api/history`：分页查询当前用户会话。
- `GET /api/history/{thread_id}`：查询当前用户的展示消息。
- `DELETE /api/history/{thread_id}`：只删除展示消息。

开发/测试环境的工作台将 `VITE_DEV_USER_ID`、`VITE_DEV_USER_NAME`、`VITE_DEV_ROLES` 转换为 `X-User-ID`、`X-User-Name`、`X-Roles` Header；身份字段不能写入 Chat 或 Resume JSON。Vite 本地开发通过 `/api` 代理访问 FastAPI；独立前端访问时仅可使用 `API_CORS_ORIGINS` 白名单中的 Origin。生产环境仍必须替换 Header 认证适配器。

M10 的 HTTP 路由已连接 M8 `ResumeService`。恢复请求只允许以下两种
结构：缺字段补充 `{kind: supplement, supplement: ...}`，或审批决定
`{kind: decision, decision: approve|reject}`。服务会校验当前用户、`thread_id`、一次性
`interrupt_id`、订单动作、resume kind、参数摘要 SHA-256 和有效期，再原子消费中断。HTTP 客户端不提交 action 或摘要哈希，这两项始终从服务端待恢复记录获取。
跨用户、篡改、过期和重放均失败关闭。

## SSE 事件

统一信封包含：`version`、`event_id`、`event`、`thread_id`、`timestamp`、`source`、`payload`。

| 事件 | 用途 |
| --- | --- |
| `token` | 文本增量 |
| `tool_start` | 工具开始 |
| `tool_args` | 脱敏工具参数 |
| `tool_result` | 截断结果或文件引用 |
| `tool_end` | 工具结束和状态 |
| `interrupt` | 补充信息或人工审批 |
| `done` | 本轮结束及是否中断 |

Agent 流同时使用 `messages` 和 `values`。每个 chunk 先检测 `values` 中的 interrupt，再处理普通消息；发生中断后发送 `interrupt` 和 `done(interrupted=true)`，然后结束本轮。

订单审批事件必须展示动作、规范化参数、金额、币种、修改差异和风险，不得只显示一句“是否确认”。工具参数和结果默认脱敏、限长。

`interrupt.payload.interrupts` 的每一项包含服务端生成的 `id` 与脱敏后的 `value`。前端恢复请求只能回传该 `id`，以及补充文本或 `approve`/`reject` 决定；动作和参数摘要仍由 Resume Gateway 从服务端记录获取。
